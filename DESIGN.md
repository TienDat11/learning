# DESIGN.md — `hitechcloud-interview-prep.html`

Visual and interaction reference. Read alongside `CONTRACT.md` (which owns the data contract).
This file records the reasoning so the next change does not re-open settled decisions.
Implementation values live in `assets/style.css` (tokens at the top of the file).

## What this is

A single self-contained HTML study tool for one person preparing for one interview
(Fullstack Engineer, AWS / Python / VueJS). 134 questions with answers, 23 lesson
schematics, quiz, flashcards, mock interview, case study, study plan, sources.
It must open offline from disk, print cleanly, and be read for long stretches.

Mode: **Operate + Read**. A study instrument, not a landing page.

## Direction: "Study bench" (Genesis system)

The UI follows the Genesis design system: neutral surfaces, one interactive colour, and
semantic colour used only for state. The goal is that a learner can tell at a glance
what matters, what is done, and where to go next.

Type:
- **Be Vietnam Pro** for display and body (page titles, lesson titles, question text, UI). Measured 102/102 Vietnamese codepoints via CDP `CSS.getPlatformFontsForNode`; General Sans (64/102 missing) and DM Sans (90/102 missing) were deleted.
- **JetBrains Mono** for code, IDs (`A01`, `L12`) and keyboard hints.
- Two weights only per screen: 400 and 600.
- All fonts are embedded as base64 (`assets/fonts.css`, generated by `tools/build-fonts.mjs`).

Colour tokens (light / dark, see `:root` and `html[data-theme="dark"]`):
- Background `#FAFAFA`, surface `#FFFFFF`, text `#0A0A0A`, border `#E8E8EC`.
- **Indigo `#4F46E5` is interactive only**: primary buttons, links, active nav, focus.
  Link and active text use `#4338CA` because it clears 4.5:1 on white.
- Semantic: red = P0 / incident / fail; amber = P1 / root cause / trade-off;
  green = done / observe / memory anchor; grey = neutral. Only the status dots,
  chips and labels take these colours. Phase labels in lessons stay neutral except through
  the dot on the rail.

Structure and information:
- **Priority is a top rule** on each question card (3px inset line, red for P0, amber for P1),
  plus a pill chip with a dot. The card body is not tinted.
- **Lessons are numbered chapters.** The header is a crumb `Vở ôn · <stageTitle> · Bài n/23`,
  then the title `<id> · <title>` (e.g. `L01 · Đọc một kiến trúc serverless từ trái sang phải`),
  then the goal, with the "Đánh dấu đã học" toggle on the right. The lesson id is the prefix
  of the title, not a separate large number. Blocks still sit on a vertical rail inside the
  notes body and each block's dot still names its phase; the `askFirst` cues and the `predict`
  card moved to the Cornell cue column and the predict card, so they are not repeated on the
  rail.

- **The memory anchor** is the only green-filled panel in a lesson (green-tinted).
- **"Hôm nay" (`view-today`): Leitner box drill over the 63 P0 deck.** A top bar shows the
  brand and `Bộ P0 · 63 câu`. A two-column grid puts the method statement on the left
  — eyebrow "Phương pháp Leitner", title "Đúng thì lên hộp. Sai thì về hộp một.", a short lede
  — and the five Leitner boxes on the right: count per box, interval per box, active box
  filled indigo. The full-width card below holds the drawn question, "Mở đáp án", then
  "Nhớ được" / "Chưa nhớ". Selection is runtime (`prio === 'P0'` via `P0_IDS` in
  `src/90-app.js`); the 134-question bank is never the drill. State is `hcp-leitner-v1` =
  `{ [qid]: { box: 1..5, due: "YYYY-MM-DD" } }`; a missing entry counts as box 1, due today.
  Draw picks a due question from the lowest box with any due question, uniformly at random
  (`LOGIC.leitnerDueQids` → `LOGIC.leitnerPick`). "Nhớ được" advances the box one level and
  schedules by the new box's interval; "Chưa nhớ" resets box 1, due today. Answer is
  `expected` if present, else `oral`; the app never authors an answer. 12 of the 63 P0 cards
  (D01, G01, G05, G10, G18, H13, J01–J06) lack `expected` — all type `concept`/`situation`,
  none `predict`/`debug` — but all 63 carry a non-empty `oral`, so every card has a real
  answer. Keyboard: Enter draws, Space toggles the answer, 1 = nhớ được, 2 = chưa nhớ; keys
  are ignored while typing in an input/textarea/select and while focus is on a button/link.
  "Sẵn sàng" reads `count(box 5) / 63` and is labelled a proposal, not a pass mark. Empty
  state shows "Hôm nay không có thẻ đến hạn." with the remaining box-1 count; there is no
  error state. `#today-reset` confirms in a dialog then deletes only `hcp-leitner-v1` and
  `hcp-recall-v1`. Intervals are `LOGIC.LEITNER_INTERVALS = [1, 2, 4, 8, 16]` days, one
  constant, the only place the schedule lives.
- **"Lộ trình học" (`view-learn`): one Cornell sheet per lesson.** A sticky position bar at
  top: `#lp-id` (`Vở ôn · <stageTitle>` verbatim), `#lp-t` (short lesson title),
  `#lp-bar` (23 segments, done = green, current = indigo, rest neutral), `#lp-n` (`n / 23`).
  Each card carries a crumb `Vở ôn · <stageTitle> · Bài n/23`, the title `L01 · <title>`,
  the goal, and the unchanged "Đánh dấu đã học" toggle (`hcp-lessons-v1`). The Cornell grid:
  left "Gợi nhớ" lists the 3 `askFirst` cues, numbered 01/02/03, each with its own toggle
  button; right "Ghi chú" holds a `n / 3 gợi nhớ đã trả lời` counter, the `predict.q` card
  with a "Hiện đáp án" button revealing `predict.a`, a covered notes panel with a "Mở ghi chú"
  button, and the notes body. Two buttons control the notes and stay in sync: the covered
  panel's primary button opens them, and a small "Che ghi chú" toggle in the notes head closes
  them — it is hidden while the notes are covered, so exactly one notes control is visible at a
  time. The predict card's button controls only the predict answer. Recall state is `hcp-recall-v1` =
  `{ [lessonId]: [cueIndex, ...] }`, a separate key. The bottom anchor band reads
  `lesson.anchor`, labelled "Tóm tắt · Câu neo". Stage headings render `stageTitle` verbatim
  ("Chặng 5 — Phòng thủ"), never shortened.
- **Mobile**: filters collapse by default. Navigation becomes a horizontal scrolling strip.
  The brand and nav sit outside `.side-body`, so they stay visible when filters are collapsed.
- **Answers are collapsed** behind a `+` summary. "Mở / Thu gọn tất cả đáp án" toggles them all.
- **Code blocks** are dark slabs with a "Chép" button. Clipboard API with a textarea fallback.
- **Flashcards** are one card, one decision. Keyboard: Space reveals, ← → navigate,
  1 = biết, 2 = yếu, `/` focuses search from any view.

Surfaces and depth:
- Flat by default. Cards carry a 1px border, not a shadow.
- Hover lift (`--hover`) only on question cards and quiz items, the browseable lists.
  Long-form lesson and answer content stays flat.
- The sidebar is sticky on desktop. It is a contents column, not a top nav, so the nav
  DOM and JS toggles stay unchanged.
- Sticky lesson position bar uses backdrop blur, not a shadow.
- No decorative gradients, dot grids, illustrations or emoji. Emoji are not in the embedded
  fonts and render inconsistently.

Motion: transitions of 150–200 ms on colour and background, a 600 ms progress-bar fill,
and a short reveal when an answer opens. `prefers-reduced-motion` disables all of it.

Content-clarity rule (lesson and question prose):
- **One case per line, and every term glossed where it is used.** Where a lesson or question explains two or more causes, failure modes or options, each gets its own line — a real `<ul>`/`<li>` inside HTML fields, and a hard line break inside plain-text fields. Two cases are never left in one running sentence, because the reader cannot see what separates them. Infra and AWS terms that a reader who has never opened the AWS console would not know (`p99`, `throttle`, `cold start`, `concurrency`, `quota`, `connection pool`, `idempotency`, `visibility timeout`, `presigned URL`, `Region`, `Availability Zone`, `DLQ`, `VPC`, `subnet`, `fan-out`, `backpressure`) are glossed inline, in plain Vietnamese, at first use — never deferred to a glossary. The English term is kept, per `CONTRACT.md`; the Vietnamese around it carries the meaning. No fact, number, quota, price or behaviour is invented to make a gloss; where a term could not be explained from a source already held, it was left bare and listed as a refusal rather than guessed.

## Deliberate deviations from Genesis

- **Indigo fill shade `#4F46E5`** instead of `#6366F1`. White text on `#6366F1` only reaches
  about 4.5:1 on the primary button. `#6366F1` is kept for focus rings and borders.
- **Stronger focus ring** (`3px` at 35% indigo, 45% in dark) instead of the faint 25% ring.
  Keyboard focus is the main way this tool is navigated.
- **Smaller display sizes.** Page title 40px (30px on mobile), question text 24px, lesson
  title 32px. Genesis's 60–72px display sizes suit landing pages, not a dense study tool.
- **Meta text `#5F5F6A`** instead of a lighter grey, to keep small text above 4.5:1.
- **Sidebar kept** rather than moved to a top nav (see above).
- **Indigo fill as a state cue.** The five Leitner boxes fill the active box with indigo —
   a state use of the interactive colour, which Genesis reserves as interactive-only.
- **Dark-theme active box paints its text dark, not white.** In light theme the filled Leitner
  box (`--accent` `#4F46E5`) carries white text at 6.29:1. In dark theme `--accent` becomes
  `#818CF8`, which is far lighter, and white on it is only 2.98:1 — below AA. The dark override
  in `assets/style.css` therefore sets the box label, the big count and the interval line to
  `#0B0B0D` (6.59:1), the same literal used by the dark primary button.
- **Sticky position bar carries one element the reference design lacks.** `#lp-t`
   (`shortLessonTitle`) shows a short lesson title between the stage label and the 23-segment
   bar. The reference design assumed a per-lesson page, so its bar needs only the stage label;
   here all 23 lessons live on one scrolling page, so the stage label alone cannot tell the
   reader which lesson they are in. The stage label (`#lp-id`) is rendered as a small sunken
   pill rather than plain text — kept because the bar is translucent over content and the
   label needs a stable backing.
- **Escaped plain-text fields keep authored line breaks.** Several content fields are plain text, not HTML, and the renderer escapes them into a `<p>` (`spokenBox`, `expectedBlock`, `oralBlock`, `fuBlock` in `src/90-app.js`; `attacksBox` sanitizes rather than escapes but its `.fa` is still authored as plain text). Default `white-space` collapsed every `\n` the author wrote, so a case-per-line enumeration re-rendered as one paragraph — the exact readability failure this pass exists to fix. `assets/style.css` now sets `white-space: pre-wrap` on `.spoken > p, .expected > p, .oral, .fu .fa, .atk .fa`. `pre-wrap` and not `pre`, so long lines still wrap. `.deep` is excluded because it carries real HTML via `sanitize()`; `.pb-out` already had `pre-wrap`, `pre` keeps `pre` with horizontal scroll on screen (`pre-wrap` only in print).

## Constraints that must hold

- Every DOM id in `REQUIRED_UI_IDS` (57 ids, `build.mjs`) and every `data-view` nav button
  must exist. Class names used by `src/90-app.js` must keep their selectors in `style.css`.
- No `<link>` tags except the favicon data URI. No external `<script src>`. No `<script>`
  inside CSS. No `@import url`.
- `node build.mjs` exits 0 with `invalid=0`. `node tests/smoke.cjs` passes — it now carries
  114 checks, 30 of them Leitner.
- Pre-existing keys `hcp-progress-v1`, `hcp-theme-v1`, `hcp-lessons-v1` are unchanged and
  never reused for new data; the two new keys are `hcp-leitner-v1` (today's drill) and
  `hcp-recall-v1` (lesson recall cues).
- Lesson schematics (`src/07-lesson-images.js`) are data and are not restyled.

## Known gaps

- Letters and Vietnamese diacritics no longer fall back: Be Vietnam Pro and JetBrains Mono measured 102/102 codepoints (`assets/fonts.css`, 12 faces). Arrows (→ ←), ✓ ✗ and a few symbols sit outside the embedded `unicode-range` subsets and still fall back to a system font as far as the CSS shows; no fresh `CSS.getPlatformFontsForNode` measurement was taken in this pass, so the exact remaining symbol set is unverified. They render, but not in the brand face.
- 390px layout was captured in `shots/today-390.png` and `shots/learn-390.png`. This is not a
  headless Chrome window render — Chrome's window minimum is about 500px — but a Chrome-based
  screenshot tool emulating device metrics at 390px, i.e. a simulated viewport rather than a
  physical device. A real-device measurement still stands as outstanding.

## Spacing schedule — what is verified and what is not

This section documents, with sources, why the review schedule shown to the learner is labelled
a proposal and not established Leitner practice.

- The original Leitner book is Sebastian Leitner's *So lernt man lernen*
  (*So lernt man lernen. Angewandte Lernpsychologie – ein Weg zum Erfolg*, Verlag Herder,
  1972, Freiburg im Breisgau/Basel/Wien, 317 pages, ISBN 3-451-16265-2). Its rule was
  **partition size**, not days: the learning box had partitions of 1, 2, 5, 8 and 14 cm,
  and cards were reviewed only when a partition filled. Remembered cards moved forward;
  missed cards moved back.
- Cepeda et al. 2006, "Distributed practice in verbal recall tasks: A review and quantitative
  synthesis", *Psychological Bulletin* 132(3):354–380, DOI 10.1037/0033-2909.132.3.354,
  PMID 16719566. It found the optimal inter-study interval grows as the required retention
  interval grows, and the relationship is non-monotonic (too long hurts). It gives no
  1/2/4/8/16-day formula.
- The app's 1 / 2 / 4 / 8 / 16 days is a **modern simplification**: fixed date markers in
  place of physical partition sizes. It is **unverified** by Leitner 1972 and by Cepeda
  et al. 2006. Wherever it is shown to the learner it is labelled as such — currently the UI
  text at `#today-note`: "Khoảng ôn 1 · 2 · 4 · 8 · 16 ngày là đề xuất chưa được kiểm chứng;
  cách tính và nguồn tham chiếu ghi trong DESIGN.md."

## Decisions still waiting on the owner

- The deck is the 63 P0 questions (`prio === 'P0'` in `P0_IDS`, `src/90-app.js`). The count
   is verified against `dist/questions.json` via jq and matches the build's METRIC lines:
   134 total = P0 63 / P1 50 / P2 21. Switching to all 134 is a one-line change in `P0_IDS`,
   but the decision has not been taken. None of the 28 questions lacking `expected` is
   `predict`/`debug` (all are `concept`/`situation`); of the 12 P0 without `expected` —
   D01, G01, G05, G10, G18, H13, J01–J06 — every card still carries a non-empty `oral` and
   `deep`, so every card has a real answer.
- The 1 / 2 / 4 / 8 / 16-day intervals are a proposal. Changing them means editing
   `LOGIC.LEITNER_INTERVALS` in `src/05-logic.js` only.
- The "Sẵn sàng" threshold (box 5 / 63) is a proposal, not a settled pass mark, and is
   labelled as such in the UI.
- 23 memory anchors (memory-palace style) were drafted at `.scratch/anchors-proposal.md`.
   They are not in the app and are not approved; gating is explicit. The app carries no
   field for them — none of `memo`/`image`/`scene`/`place`/`visual`/`mnemonic`/`palace`
   exists on any of the 23 lessons — so shipping them is a data-shape change, not a render
   change.
- The content audit (`node build.mjs` METRIC lines) is the source of truth for counts.
   Do not hand-copy numbers that could drift — where a count is quoted here, the file or
   command it came from is named.
- A small set of terms was deliberately left unglossed rather than explained from memory: `throttling`, `provisioned capacity`, bare `DynamoDB`, the API Gateway integration timeout, `message_id`, `migration`, `build image`, `health check`, `logging`, and bare `timeout`/`retry`. Explaining them properly needs a source fact the content pass did not hold, and inventing one was refused. They read as bare jargon until a source is added.
